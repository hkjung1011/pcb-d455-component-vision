IoTKITs 1,053장과 Embedded Hardware 960장을 합쳤습니다. 외부 평가용 Commons 44장과 유사한 이미지가 포함된 그룹 전체를 제외하면서 IoTKITs 후보 15장이 제외됐습니다. 이는 확정 중복 15장을 뜻하지 않으며 보수적 유사도 제외입니다.

실제 파일·라벨 오류 0건, 설정된 회전·반전 pHash 기준의 분할 간 유사 후보 0건, holdout 유사 후보 0건으로 **구조 검증은 통과**했습니다. 이 검사는 의미상 모든 유사 사진을 찾아낸다는 보장이 아닙니다. **Nucleo가 val/test에 없어 9클래스 학습·평가 준비는 미완료**입니다. 이전의 단순 `pass` 결과를 학습 준비 완료로 해석하면 안 됩니다.

Embedded의 STM32 393개 크롭은 Nucleo-64 계열, Pi 363개 크롭은 Pi4로 전수 검토했습니다. 공급자 영상은 10개지만 전체 이미지 pHash로 연결하면 960장이 한 그룹이 됩니다. 실제 다른 보드도 같은 배경 때문에 유사 후보로 연결된 사례가 있어, 이를 진짜 중복이라고 단정하지 않았습니다. 이번에는 이 연결을 보수적으로 유지했으며 독립된 Nucleo val/test 자료가 필요합니다. 자세한 근거는 [그룹 검토](GROUP_SUPPORT_REVIEW.md)에 있습니다.

## 포트 모델 B

라즈베리파이 549장의 기존 박스를 목표 클래스로 변환해 staging에 보존했습니다. 전체 라벨 완전성 확인이 끝나지 않아 학습 데이터셋 `ports_v1`은 생성하지 않았습니다.

- vniye의 실제 이름은 숫자 문자열입니다. 사진 대조 결과 `6 → hdmi`, `7 → micro_usb`로 정정했고, `4 → ethernet_port`도 전체 사진 문맥에서 확인했습니다. YOLO의 숫자 ID와 이름 문자열을 혼동하지 않도록 매핑했습니다.
- dpiwf에는 보이는 표준 HDMI와 micro HDMI의 라벨이 빠져 있습니다. 방열판은 클래스 부재만 확인했으며 실제 누락 여부는 추가 검토가 필요합니다.
- `usb_stack`은 2단 USB-A 하우징 단위입니다. Nucleo 원본의 `ST-LINK V3`는 디버거 MCU 칩이므로 목표 `st_link` 영역 정의를 먼저 확정해야 합니다.
- 표본으로 의미가 맞는 매핑과 모든 사진의 라벨 완전성을 구분했습니다. 상세 내용은 [포트 매핑 검수](PORTS_MAPPING_REVIEW.md), 기계가 읽는 대응표는 [class_mapping.csv](class_mapping.csv)에 있습니다.

## 수정한 준비 도구

가져오기에서 ZIP 경로 이탈·잘못된 라벨·상충 중복을 검사하고 원본 클래스/박스/분할/해시를 남깁니다. 영상 프레임·증강본·같은 촬영 장면은 같은 분할 그룹으로 묶습니다. 보류된 포트 매핑이 확정된 보드 라벨까지 막지 않도록 모델별로 판단하고, 포트는 `verified_complete` 상태만 내보냅니다.

검증 결과는 `structure_pass`와 `training_ready`를 구분합니다. 학습 진입 시 데이터·매핑·holdout 해시와 준비 상태를 다시 검사하도록 수정했습니다. 정상 자료, 빠진 클래스, 오래된 검증, 회전 누수, 잘못된 라벨을 대상으로 한 검증 fixture도 확인했습니다. 실제 학습은 수행하지 않았습니다.

## 이어서 필요한 작업

1. Chrome에서 차단된 STM32 107장 ZIP을 확보한 후 크롭 검수와 촬영 그룹 확인을 진행합니다. ZIP 하나가 추가돼도 독립 Nucleo val/test 장면이 충분하다는 보장은 없습니다.
2. Nucleo의 독립 촬영 자료를 추가 확보하거나, 영상별 배경 유사 후보를 보드 크롭 등으로 판별한 근거를 마련합니다. 준비 상태를 통과시키려고 중복 임계값만 완화하지 않습니다.
3. 포트 목표 정의를 확정하고 빠진 라벨을 보완·검수한 이미지에만 `verified_complete`를 부여합니다. 초안은 평가에 사용하지 않습니다.
4. 가져오기 → 합치기 → 검증을 다시 실행합니다. 이번 작업 범위는 데이터 준비까지이며, 학습은 별도 지시 후 진행합니다.
